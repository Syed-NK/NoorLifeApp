# Phase 6C-3C — Authentication callback contract and audit

Branch `feature/subscriptions-family-six`, from `e213471`.

This document is the audit required before any code changed, and the contract every callback file
below implements. It is written first on purpose: a deep link is an **untrusted input that can
establish a session**, and a trust boundary invented while typing is a trust boundary nobody
reviewed.

### 1.2 Application scheme and deep-link configuration

`app.json` declares `"scheme": "noorlifeapp"` and lists the `expo-router`, `expo-splash-screen` and
`expo-secure-store` config plugins. There is no `ios.associatedDomains`, no
`android.intentFilters` and no universal/App Link configuration — callbacks are **custom-scheme
only**, which is what this contract assumes.

`android/` is **not checked in**: `.gitignore` ends with `/ios` and `/android`, and
`git ls-files android` returns nothing. Both native projects are generated by `expo prebuild`.
That is load-bearing for §3 — there is no hand-edited manifest to keep in step, and no prebuild
was needed to make the backup rules correct because they were already correct.

Generated `android/app/src/main/AndroidManifest.xml`, `MainActivity`:

```xml
<activity android:name=".MainActivity" android:launchMode="singleTask" android:exported="true" …>
  <intent-filter>
    <action android:name="android.intent.action.MAIN"/>
    <category android:name="android.intent.category.LAUNCHER"/>
  </intent-filter>
  <intent-filter>
    <action android:name="android.intent.action.VIEW"/>
    <category android:name="android.intent.category.DEFAULT"/>
    <category android:name="android.intent.category.BROWSABLE"/>
    <data android:scheme="noorlifeapp"/>
    <data android:scheme="exp+noorlifeapp"/>
  </intent-filter>
</activity>
```

Two facts matter downstream:

* `android:launchMode="singleTask"` means a second link delivered while the app is running
  re-uses the existing task and arrives as an `onNewIntent` — i.e. a **warm-start** `url` event,
  never a second process. Warm-start handling is therefore mandatory, not optional.
* `exp+noorlifeapp` is Expo Go's scheme. It is declared by the prebuild and this contract does
  **not** trust it: a callback is accepted on `noorlifeapp` only. Expo Go is not a supported target
  for authentication callbacks in this project, which is already true — the app requires a
  development build (`expo-dev-client`).

iOS URL scheme: no `ios/` directory exists in the working tree, so nothing is checked in to audit.
The scheme is contributed by `app.json` at prebuild time and would appear in
`Info.plist` `CFBundleURLTypes`. No iOS build was produced in this phase; that is reported, not
claimed.

### 1.4 Current PKCE implementation, read from `@supabase/auth-js@2.111.0`

Audited in `dist/main/lib/helpers.js` and `dist/main/GoTrueClient.js`:

* `getCodeChallengeAndMethod(storage, storageKey, isPasswordRecovery)` mints a verifier, appends
  `"/recovery"` to the **stored** copy when the call is `resetPasswordForEmail`, stores it under a
  per-flow slot key *and* the legacy fixed key `<storageKey>-code-verifier`, then returns
  `codeChallengeMethod = codeVerifier === codeChallenge ? 'plain' : 's256'`.
* `resetPasswordForEmail` calls `_maybeAppendFlowIdToRedirect(options.redirectTo, flowId)`, which
  appends `sb_flow_id=<flowId>` to the redirect URL (`PKCE_FLOW_ID_PARAM = 'sb_flow_id'`) **only when
  `auth.experimental.appendPkceFlowIdToRedirects` is enabled**. It defaults to `false` and returns
  `redirectTo` unchanged.

  > **Correction (2026-08-03).** The original text of this section stated that the SDK appends
  > `sb_flow_id` unconditionally. That was wrong, and the application shipped on it: every redirect
  > went out bare, and every exchange fell back to the legacy fixed verifier key. The SDK's own
  > documentation for the flag is explicit — flows that offer no way to obtain the flow id (email OTP,
  > password recovery, sign-up confirmation) "can only be correlated via this flag". It is now
  > enabled in `src/lib/supabase.ts`.
* `exchangeCodeForSession(authCode, { flowId? })` resolves the verifier — **slot-only when a
  `flowId` is given, no fallback to the legacy key** — splits it on `/`, POSTs
  `token?grant_type=pkce`, removes the verifier, saves the session and notifies
  `redirectType === 'recovery' ? 'PASSWORD_RECOVERY' : 'SIGNED_IN'`. It returns
  `{ data: { user, session, redirectType }, error }`.
* A missing verifier throws `AuthPKCECodeVerifierMissingError` **before** any network call.

Three consequences this contract relies on, none of them invented:

1. `data.redirectType === 'recovery'` is the SDK's own, authoritative discriminator for a password
   recovery callback. Nothing needs to be inferred from the URL.
2. The verifier is single-use and deleted on both the success and the failure path, so a replayed
   link cannot exchange twice — the second attempt fails with a verifier-missing error rather than
   minting a second session.
3. `sb_flow_id` must be read off the callback URL and passed through as `options.flowId`, because
   the deprecation-window legacy key mirrors only the *most recently started* flow. Passing it is
   the documented usage (`GoTrueClient.exchangeCodeForSession`'s own example does exactly this).
   It only *arrives* on the URL when the experimental flag above is on — which is what makes two
   concurrent email flows safe rather than a coin toss over one shared verifier slot.
4. `sb_flow_id` is **reserved**. `appendFlowIdToRedirectTo` strips any value already present in
   `redirectTo` and substitutes the SDK's own, and the value names a verifier storage slot — so a
   self-minted one makes `exchangeCodeForSession` throw `AuthPKCECodeVerifierMissingError` locally,
   with no network call. NoorLife's own flow-intent discriminator is a separate parameter, `nl_rid`;
   see `src/services/auth/pending-auth-flow.ts`.

### 1.5 The WebCrypto / plain-code-challenge warning

`generatePKCEChallenge` in `@supabase/auth-js@2.111.0`:

```js
const hasCryptoSupport = typeof crypto !== 'undefined' &&
    typeof crypto.subtle !== 'undefined' &&
    typeof TextEncoder !== 'undefined';
if (!hasCryptoSupport) {
    console.warn('WebCrypto API is not supported. Code challenge method will default to use plain instead of sha256.');
    return verifier;
}
```

`react-native@0.86.0` installs no `crypto` global (`Libraries/Core/setUpGlobals.js` sets `window`,
`self` and `process` and nothing cryptographic), and no installed package polyfills one:
`react-native-url-polyfill` ships only `URL`/`URLSearchParams`, and `expo`/`expo-modules-core`
contain no `crypto.subtle` reference. So **before this phase the app fell through to
`code_challenge_method=plain`**, which removes the entire protection PKCE exists to provide: a
`plain` challenge *is* the verifier, so anyone who can observe the authorization request can
complete the exchange.

That is the blocker §5 resolves. It is stated here rather than in a release note because it was a
real security shortfall in the audited build, not a theoretical one.

### 1.6 Email-action redirects, before this phase

`src/services/auth/auth.service.ts` resolved one lazily-memoized value:

```ts
cachedRedirect = AuthSession.makeRedirectUri({ scheme: 'noorlifeapp' });
```

`makeRedirectUri` delegates to `Linking.createURL('', { scheme })`, which in a development or
release build yields the **bare scheme root** `noorlifeapp://`. That value was passed to:

* `signUp({ options: { emailRedirectTo } })`
* `resetPasswordForEmail(email, { redirectTo })`
* `signInWithOAuth({ options: { redirectTo } })` and `WebBrowser.openAuthSessionAsync(url, returnUrl)`

`requestEmailChange` in `src/services/account/account-security.service.ts` called
`updateUser({ email })` with **no** `emailRedirectTo` at all, so an email-change confirmation had
no application destination.

### 1.7 What consumed a callback, before this phase

Nothing. `grep` for `expo-linking` in `src` found three call sites — `external-link.service.ts`,
`notification-permission.service.ts` and `reset-link-sent-screen.tsx` — all of which *open* URLs.
There was no `getInitialURL`, no `addEventListener('url')` and no `/auth/callback` route. A user who
clicked a real confirmation or recovery link landed on the entry gate with the code discarded.

`src/features/entry-auth/screens/new-password-screen.tsx` read `params.code` and showed a banner
when it was absent, but it never exchanged the code — `resetPassword` calls
`updateUser({ password })` against whatever session happens to exist. Reached with a live ordinary
session and no recovery context, that screen would change the signed-in account's password. §7
closes that.

### 1.8 AuthProvider and startup routing, before this phase

`AuthProvider` resolves `getSession()` once, subscribes to `subscribeToAuthChanges` and calls
`adopt(user)`. `adopt` treats an **unconfirmed** account as signed-out with
`pendingVerificationEmail` set, which is what stops Verify Email being bypassed. It ignores the
event *name*, so a `PASSWORD_RECOVERY` event is indistinguishable from `SIGNED_IN` at that layer —
recovery context therefore cannot live in `AuthProvider`, and §7 puts it in its own boundary.

`useStartupRouting` feeds one pure machine (`startup-machine.ts`) and **freezes** the destination
the first time one is named. `nextStartupState` requires `hasCompletedPlanSelection === true` before
`authenticated_home`; anything else signed-in goes to `subscription_choice`. That is the
authoritative post-auth decision and this phase does not add a second one.

There was no intended-destination or deep-link preservation of any kind.

### 1.9 Supabase Dashboard redirect allow-list, as documented in the repository

Not documented anywhere before this phase. `docs/` contained no redirect URL list, and
`supabase/config.toml` governs the *local* stack only. §8 adds the required list.

## 2. The callback contract

### 2.1 One canonical URL, declared once

```
noorlifeapp://auth/callback
```

Declared as data in `src/services/auth/auth-callback.config.ts` and nowhere else. No service, screen
or test spells the string itself; `auth-callback-source-scan.test.ts` asserts that.

It is built from constants rather than from `Linking.createURL`/`makeRedirectUri` deliberately. The
value has to match a Supabase Dashboard allow-list entry **exactly**, and a value that varies with
the execution environment (Expo Go yields `exp://<lan-ip>:8081/--/…`) cannot be allow-listed
honestly. Expo Go is out of scope for callbacks and this project already requires a development
build.

### 2.2 Accepted

A URL is a NoorLife authentication callback only if **all** of these hold:

| Requirement | Value |
| --- | --- |
| Scheme | `noorlifeapp` exactly, case-insensitive, no other scheme |
| Authority + path | resolves to the single path `auth/callback` |
| Payload | a `code` matching `^[A-Za-z0-9._~-]{20,512}$` |
| Flow, when declared | `type` ∈ { `signup`, `recovery`, `email_change`, `magiclink`, `invite` } |
| Flow id, when present | `sb_flow_id` matching `^[A-Za-z0-9_-]{8,64}$` (the SDK's own pattern) |

Custom-scheme URLs are parsed with the host-or-path tolerance a real device needs:
`noorlifeapp://auth/callback`, `noorlifeapp:///auth/callback` and a trailing slash all resolve to
the same path. `noorlifeapp://auth/callback/extra` does not.

### 2.3 Rejected, with the sanitized code each produces

| Condition | Code |
| --- | --- |
| Any scheme that is not `noorlifeapp` — including `exp+noorlifeapp`, `https`, `javascript` | `untrusted-scheme` |
| An authority that is not part of the approved path | `untrusted-host` |
| A path other than `auth/callback` | `unsupported-path` |
| No `code` and no `error` | `missing-code` |
| A `code` outside the shape above, or repeated with different values | `malformed-code` |
| `type` present but not in the supported set | `unsupported-flow` |
| `type` declares recovery and the exchange reports non-recovery, or the reverse | `conflicting-flow` |
| Tokens in the fragment (`#access_token=…`) | `invalid-link` |
| The same callback delivered again after it was consumed | `link-already-used` |
| GoTrue reports an expired or already-used link | `link-expired` / `link-already-used` |
| Transport failure | `offline` |
| Anything else | `server-error` |

Duplicate delivery of an *unconsumed* callback with the same `code` is **not** an error: it is
collapsed to the single pending callback already held, which is what `singleTask` warm delivery
produces in practice.

### 2.4 Never logged, never rendered, never persisted by us

* the authorization `code`
* `sb_flow_id`
* any access or refresh token
* `error_description` (it is a server-authored string that has carried addresses and identifiers)
* the complete callback URL, in any form, including inside an `Error` message

Only the sanitized codes in §2.3 reach the UI, a log line or a thrown error. The parser's rejection
value carries a code and nothing else — there is no field on it that could hold a secret.
`auth-callback-source-scan.test.ts` enforces this by reading the source.

### 2.5 Flow classification, and what is authority

| Signal | Status |
| --- | --- |
| `type` on the URL | **hint only.** Cross-checked, never trusted alone. |
| `data.redirectType` from `exchangeCodeForSession` | **authority** for recovery. Comes from the verifier this device stored when it started the flow. |
| Refreshed `auth.users` via `getUser()` | **authority** for the account's email and its pending change. |

A conflict between the hint and the authority is a rejection, not a resolution. Signup confirmation
and email-change confirmation both produce a non-recovery `redirectType`; they are told apart by the
refreshed user, never by a URL parameter, and neither is allowed to bypass the startup machine.

### 2.6 Legacy fragment-token callbacks are deliberately unsupported

`flowType: 'pkce'` means every email action this app initiates issues a PKCE link, so a
fragment-token (implicit) callback can only arrive from a customised GoTrue email template or a
hand-built URL. Supporting it would mean accepting an access and refresh token straight off an
untrusted input and handing them to `setSession` — the single highest-value thing a deep link could
smuggle, for a flow the application never asks for.

So there is no `setSession` path in the callback service at all. A fragment-token callback is
rejected as `invalid-link` and the user is told to request a new link. The cost is stated rather
than hidden: **this contract requires the project's default confirmation and recovery email
templates.** If a template is ever changed to an implicit link, callbacks will be refused rather
than silently downgraded.

### 2.7 OAuth is reserved, and why nothing is wired for it

`signInWithGoogle` consumes its own callback in-process through
`WebBrowser.openAuthSessionAsync`, which resolves with the return URL — the deep-link listener is
never involved. So there is nothing for this contract to add, and production Google/Apple OAuth
stays disabled as instructed. The `oauth` flow name is declared in the configuration so a later
phase has one place to enable, and the parser refuses it today.

## 3. Android backup rules — the documentation correction

The rules are correct (§1.10), so the change this phase makes is to the *claims* about them, in
`src/features/profile/privacy-security-copy.ts`. The existing comment already described the
behaviour accurately, but the distinction it drew was easy to read past: ordinary preferences
**are** included in cloud backup and device transfer, and the SecureStore file is the only thing
excluded. `secure-store-backup.test.ts` now asserts that distinction against the generated and
merged configuration rather than against a comment, so a future prebuild or SDK bump that drops the
exclusion fails a test instead of quietly widening what leaves the device.

iOS: `expo-secure-store` defaults to `kSecAttrAccessibleWhenUnlocked`, which is **not** a
`ThisDeviceOnly` class, so a Keychain item can be carried into an encrypted device backup and
restored onto another device. This phase does **not** change the accessibility class: moving to
`WHEN_UNLOCKED_THIS_DEVICE_ONLY` would silently invalidate the stored session on every device
migration, which is a login-and-session decision that needs its own evaluation. Nor does anything
claim uninstall removes Keychain items — it is not guaranteed to.

## 4. Routing

### Signup confirmation

Exchange, then hand over to the authoritative startup state. The callback screen never decides
between onboarding, the plan chooser and Main Home; it navigates to the entry gate, which runs the
one existing decision in `startup-machine.ts`. `hasCompletedPlanSelection !== true` still means
`subscription_choice`, so a confirmed signup **cannot** reach Main Home without passing the plan
chooser.

### Password recovery

`redirectType === 'recovery'` establishes a recovery context in `AuthCallbackProvider` — an
in-memory, non-persisted grant with the user id it was minted for. `/auth/set-new-password` renders
only while that grant is live; without it the screen shows an expired-link state and offers a fresh
request. On success the grant is consumed and cleared, replay is refused, and the user is routed by
`router.replace` so Back cannot return to a completed recovery. The authenticated
`/profile/privacy-security/change-password` route is never used as a recovery substitute, and
`new-password-screen.tsx` no longer submits without a grant.

### Email change

Nothing on the URL becomes a displayed address. After the exchange the callback service calls
`getUser()` and the screen renders only what the refreshed user reports: the confirmed address when
`new_email` is empty, and an honest "still awaiting confirmation on the other address" state while
Secure Email Change has one side outstanding. Secure Email Change is not disabled.

### Cold start

`Linking.getInitialURL()` is read once inside `AuthCallbackProvider`, above the router, so the link
is captured before fonts, session and onboarding have resolved and cannot be lost to that race. The
native splash handoff is untouched. While a callback is pending the entry gate resolves to
`/auth/callback` **instead of** the startup destination, so nothing lands on Home before the
callback has been processed.

### Warm start

`Linking.addEventListener('url')` delivers the `singleTask` re-entry. The provider holds one pending
callback keyed by its code, so a duplicated delivery is collapsed rather than exchanged twice, and
`claim()` hands it out exactly once. A URL that is not a callback is ignored completely — the
current screen keeps its state, and an invalid callback shows its state without unwinding the stack.

### Intended destination

A single sanitized slot: an app-internal absolute path from a bounded allow-list of prefixes, never
an external URL, never a protected route on its own authority. Subscription and entitlement gates
run afterwards exactly as they do for any other navigation. Cleared on use.

## 5. PKCE and S256

`src/services/auth/web-crypto.ts` installs, **only where the global is missing**:

* `crypto.getRandomValues` — `expo-crypto`'s native CSPRNG
* `crypto.subtle.digest('SHA-256', data)` — `expo-crypto`'s native SHA-256, returning an
  `ArrayBuffer`
* `TextEncoder` — minimal UTF-8 encoder
* `btoa` — minimal base64 encoder

Imported for its side effect at the top of `src/lib/supabase.ts`, before `createClient`, because
`getCodeChallengeAndMethod` reads the globals at call time and the client must never be constructed
against a half-installed environment.

`describePkceChallengeMethod()` reports `'s256'` or `'plain'` from the globals actually present. It
is asserted in tests and captured on device. **If it ever reports `plain`, the build is not
production-ready and this document is the place that says so.**

## 7. Required Supabase Dashboard configuration

This code cannot and does not configure the remote project. **Authentication → URL Configuration →
Redirect URLs** must contain:

```
noorlifeapp://auth/callback
noorlifeapp://auth/callback?**
```

The second entry is required because every redirect NoorLife sends now carries `nl_rid`, and the SDK
appends `sb_flow_id=<flowId>` on top of it once `appendPkceFlowIdToRedirects` is enabled — while
Supabase matches redirect URLs by glob, so a bare entry stops matching the moment any query string is
present.

Until those entries exist, GoTrue substitutes the project's Site URL and the emailed link will not
return to the application. That is a dashboard action, reported here rather than attempted.

Production SMTP remains **deferred**: Supabase's built-in mailer allows only a few messages per hour
and is not for production. Until custom SMTP is configured, a confirmation or recovery message may
simply not arrive — which is why the affected screens say so plainly and why the device evidence for
this phase uses fixtures and shaped ADB links rather than live email.
